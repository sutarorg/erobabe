# Fixing legacy Streamtape "Client blocked" playback errors

## Why this happens

The message **"Client blocked! Your browser or the embed you are viewing are doing nasty things!"** is generated by Streamtape. It means Streamtape has rejected the embed/request under its own access or anti-abuse rules. The Erobabe page cannot reliably repair a provider-side rejection, and changing iframe headers, disguising traffic, or trying to bypass Streamtape's protections is not a dependable or appropriate fix.

The Streamtape integration was retired. Current video publishing supports direct MP4 URLs, but legacy records can still contain Streamtape embed URLs, so those old embeds may continue to fail.

## Recommended resolution

1. Open the Erobabe admin video editor for the affected video.
2. Obtain a legitimate, direct .mp4 playback URL from a host you control or are authorized to use. A normal webpage URL or a Streamtape embed URL is not a direct MP4 URL.
3. Update the video to use the direct MP4 URL through the existing direct-URL publishing workflow. Confirm the URL plays in a browser before publishing.
4. If the source only provides a Streamtape embed and no authorized direct media URL, replace it with a provider that explicitly supports embedding, or remove/unpublish the broken video. Do not try to defeat the provider's access controls.
5. Test the public video page on desktop and mobile.

## Troubleshooting

- **Direct MP4 returns 403/404:** verify the host permits public playback and cross-origin media requests, and that the URL points to the media file rather than an HTML page.
- **Video works on the host but not on Erobabe:** inspect browser DevTools Network/Console for host hotlink protection, CORS, TLS, or URL-expiration errors.
- **Only old Streamtape videos fail:** migrate those legacy records; changing the Erobabe iframe alone cannot make Streamtape serve a blocked embed.

## Scope

This guide documents the supported recovery path. It does not claim to bypass Streamtape's block page or automatically rewrite existing database records. Any bulk migration should be performed only after validating replacement URLs and backing up the affected records.
